## Measured response behavior

CSV: two hops.
1. `docs.google.com/.../pub?...output=csv` → **HTTP 307**, `cache-control: no-cache, no-store, max-age=0, must-revalidate`, `Location: https://doc-0k-bg-sheets.googleusercontent.com/pub/<a>/<b>/<epoch-ms>/<user>/*/e@2PACX...?gid=...`
   - The `<epoch-ms>` in the redirect target is the current time **rounded to 5 s** (1790983325000 = 23:22:05, 1790983330000 = 23:22:10). The `<b>` segment also rotated between requests. Any query string you add (`&_=123`) is carried into the Location URL.
2. `googleusercontent.com` → **HTTP 200** `text/csv; charset=utf-8`, `cache-control: private, max-age=300`, `vary: Accept-Encoding`, no ETag / Last-Modified.

HTML (`pubhtml/sheet`): single **HTTP 200**, `cache-control: no-cache, no-store, max-age=0, must-revalidate`.

CORS (tested with `Origin: http://localhost:5173`): the 307 returns `access-control-allow-origin: http://localhost:5173`, the googleusercontent 200 returns `access-control-allow-origin: *`, and `pubhtml/sheet` echoes the origin. **So a browser on localhost can fetch both CSV and HTML directly.** A proxy is not required for the sheet (it is still recommended; see stack.md).

Latency: all three requests in parallel took ~850 ms from Node.

## Freshness: what to expect

- **Our side (fully controllable):** the 307 hop is `no-store`, and its target URL changes every 5 s, so a browser HTTP cache can only serve the `max-age=300` copy if two loads land in the same 5 s bucket. To remove even that, fetch with `cache: 'no-store'` and add `&_=${Date.now()}` (verified that the param passes through and the content is unchanged). From Node there is no HTTP cache at all.
- **Google's side (not controllable):** the published copy is regenerated by Google when "Automatically republish when changes are made" is on. Public reports and Google's own wording describe **a delay of about 5 minutes, sometimes longer**, between an edit and the published output. Cache busting cannot get around this server-side republish delay. I could not measure it directly because we have no edit access to the sheet. **To measure it:** have the league owner edit one cell and note the time, then run `INTERVAL=30 DURATION=1800 node scratch/freshness-poll.mjs`. It hashes the Drafts CSV, the Board CSV, and the board HTML table every 30 s and logs each change to `scratch/freshness-log.txt`, which shows how long the change took to appear on each endpoint.
- **App behavior:** fetch fresh data on every page load (the requirement), show a "fetched at HH:MM:SS" stamp, and show a note that the league sheet can lag by about 5 minutes. A manual "Refresh" button is cheap. Do not poll aggressively; Google may rate-limit.

## Red = taken: evidence

- **On this sheet, "red" is red text (`color:#ff0000`), not a red background.** The styled HTML has 7 CSS classes (`s0`…`s6`); only `s5` has `color:#ff0000`; every class has `background-color:#ffffff`. 88 cells resolve to red text, which is 44 Chinese/English pairs = 44 taken Pokémon. A plain `class="s5"` grep finds only 86, because some cells are `class="s5 softmerge"`, so match the class list rather than an exact attribute. No pair has only one half red.
- Class names are **regenerated per render** (`s5` today may be `s7` tomorrow), so the parser reads the inline `<style>` rules `.ritz .waffle .sN{...}` and resolves each `<td class="sN">` to its `color` and `background-color`. It flags a cell as red if either color is reddish (R ≥ 180, G ≤ 120, B ≤ 120). That catches `#ff0000`, `#e06666`, `#cc0000`, and `#ea4335`, and it still works if the owner switches to red fill.
- `colspan` must be honored when assigning column indices (the tier header row uses `colspan="2"`, except "11 Points", which sits in a single cell followed by an empty cell; both layouts give the same column).
- Some text sits inside `<div class="softmerge-inner">`. Strip tags to get it.

- Draft order seen so far: coaches 1–4 have 5 picks and 5–10 have 4 picks, so **Anthony (#5) is next** in round 5 (round 5 runs 1→10).

**Recommendation:** use the **Drafts tab CSV as the source of truth** for ownership, points, and the remaining budget. It carries who drafted what, which red cells do not. Use the board CSV for the pool and tiers. Fetch the board HTML as a **consistency check only**: show a warning badge if a red name is not drafted, or a drafted name is not red. A mismatch usually means a typo, or that the owner updated only one tab. Taken = drafted ∪ red, so nothing taken can show as available.

## Parsing approach (implemented in `scratch/sheet.mjs`)

- `parseCsv` is a 25-line RFC 4180 parser (quotes, `""`, CRLF). No dependency needed.
- **Board CSV:** find the row with `/^\d+ Points?$/` cells. Each tier header at column `c` owns columns `(c = Chinese, c+1 = English)`. Every later row yields `{points, zh, en}` where `en` is non-empty. Trim everything (names have trailing spaces).
- **Drafts CSV:** row 0 has `"N.Name"` at columns 0, 3, 6, …, so each coach owns 3 columns `(zh, en, points)`. Rows from index 2 are picks in round order. A row whose English cell is `Points Left` gives the remaining budget in the points column. Coach names include `Hex(法拉)`, `17`, and `DIngDIng`; keep them as-is.
- **Board HTML:** `redNamesFromBoardHtml(html)` returns `[{points, en, zh, red, how: 'text'|'background'|null}]`.
- **Names:** map each English name through `scratch/name-map.mjs` (`makeNormalizer`). Never compare raw strings across tabs.

## Failure modes to handle

- Google returns an HTML sign-in or error page instead of CSV (unpublished sheet): check `content-type: text/csv`.
- The owner inserts columns or rows: parsing is header-driven (tiers, `N.Name`, `Points Left`), not by fixed offsets.
- New typos: unmatched names surface in the UI as "unknown Pokémon: X" with a fuzzy suggestion. They are never silently dropped.
